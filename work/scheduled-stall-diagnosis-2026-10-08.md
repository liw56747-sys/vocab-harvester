# 定时任务无进展弹窗诊断（2026-10-08）

## 现场证据

- 本机日志 13:16:53 确认运行版本 1.7.10。
- 同一任务 13:17:18 启动，未见结束即于 14:01:14 再次启动；13:17:29 同时还有手动抓取线程使用 BrowserPool。
- 14:01:44 新增 BrowserPool[1] new_context 超时警告；14:41:14 第二次启动满 2400 秒时触发无进展分支，并导出 0 条。
- 期间 X 多次 SearchTimeline HTTP 200，并有提取 50/100 条主帖和评论的日志；14:41:04、14:41:53 仍有评论采集记录。旧 Cookie 的 403 故障不能解释全部现象。
- 每次定时执行的线程都名为 sched-crawl_0，底层抓取日志不含独立运行 ID，不能将每条评论日志唯一归属于某一轮任务，也不能断言第二轮本身一直有进展。

## 源码确认的缺陷

- run_scheduled_task_now 和 _execute_scheduled_task 未阻止同一任务重入；重载调度器也不能保证旧运行已结束。
- BrowserManager/BrowserPool 为进程全局单例，不同线程和事件循环复用同一 Playwright 对象；更换 asyncio.Lock 并不能迁移浏览器所属事件循环。与并发启动后的 new_context 超时高度相关，具体悬挂调用还缺独立运行 ID/堆栈证据。
- 心跳仅在关键词/补抓轮次开始时更新，未传入滚动和评论分页；持续有效抓取也可能超过无进展阈值。
- 超时分支对所有所选平台生成相同错误、覆盖 posts 为 {}；并未逐平台确认卡死，也不保留工作线程中已有结果。
- shutdown(wait=False) 和重置单例引用不会取消在运行的线程、协程或浏览器；“已自动中止”不能证明底层工作已停止。

## 修复方向与测试边界

阻止同任务重入；按执行线程/事件循环隔离浏览器生命周期；以有效数据与分页进展刷新心跳；加入可确认的取消与清理；保留部分结果和逐平台状态；给每轮执行添加运行 ID。

现有定时回归使用模拟抓取结果，新增 X 会话轮换回归也未覆盖多执行并发、长时间评论与看门狗取消组合。本轮为诊断，没有修改产品代码或发布。


## 修复实施（纳入 v1.7.11）

- 同一个任务的立即执行、cron 和调度器重载共用占用记录；线程真正退出前不得再次启动。
- 调度器复用现有实例，仅更新未来的调度，不 shutdown 正在运行的作业；过期状态恢复排除本进程在途任务。
- 浏览器管理器和进程池归属于各自事件循环；手动与定时线程退出时只关闭自己的浏览器。使用次数回收不会中断仍有 context 的浏览器；Playwright stop 有等待上限。
- 新主帖、评论页和有效分页推进更新单调时钟心跳，无新增的重复滚动不延长任务存活时间。
- 抓取期间将过滤后的主帖/评论增量映射成结果快照；保留主帖关联、历史去重与数量限制。后续阶段失败或取消不会清空已保存快照。
- 看门狗向所属循环发送真实取消请求，并等待退出；后台若暂未响应，保存快照、明确提示“停止尚未确认”，继续阻止重入，不假装线程已被杀死。
- 已完成平台、停止的平台和未执行的平台分别记录；部分结果可保存 CSV/Excel，界面显示“部分完成”和汇总数量。
- 每轮执行使用独立运行 ID 和线程名，便于后续日志归属。

## 验证方式与限制

- 真实线程/事件循环运行新增定时回归；通过模拟时间推进验证超过 40 分钟仍有进展，以及无进展触发取消，无需实等 40 分钟。
- 实际运行临时数据库、Pipeline 和 CSV/Excel 写入，核对取消后的主帖、评论和父帖关联。
- 使用真实 APScheduler 验证重载不取消在途作业；使用两个真实 Chromium 验证一轮关闭不影响另一轮。
- 实际前端页面验证三种抓取流程的汇总/下载、部分完成弹窗、任务列表和重复执行拒绝。
- 外部平台数据使用模拟；这不代表已经完成真实账号数小时抓取或 Windows 故障电脑复测。Python 无法安全强杀任意阻塞线程，因此无法确认退出时保留占用并明确提示，不允许重叠启动。
- 修复阶段仅修改本地源码；用户随后授权推送及发布，现将修复纳入 v1.7.11。发布流程不会替换已安装客户端。
