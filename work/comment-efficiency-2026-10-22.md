# 评论采集效率优化（v1.9.1）

2026-10-22，接续工作台和分阶段采集改造。当前安装版本 v1.9.0 尚不会自动获得这些源码修改。

## 问题与改动

1. **结果缺口被当作全平台故障。** 原逻辑给每个未完成评论结果创建普通异常，连续结果不足会导致平台等待从 2 秒翻倍，最高 120 秒。现在保留结构化原因；数量缺口、单帖上限、帖子不可访问不会触发指数退避。429、网络故障、平台服务异常仍退避；未知错误只采用小幅等待，不不断翻倍。
2. **X 重复创建资源。** 任务内复用评论浏览器上下文和标签页。每个上下文最多服务 20 个主帖后回收；页面正常完成后导航到 `about:blank`，停止上一帖后台流量并清空页面，再交给下一帖。网络异常或取消会丢弃页面；上下文关闭后下次重建。资源拦截仅注册一次。
3. **Reddit 重复建立连接。** 任务内复用评论 HTTP 客户端，保留搜索阶段已确定的可用端点与会话 Cookie，继续保留后续响应更新的 Cookie。完成、失败、取消均关闭连接。独立调用原抓取器时仍由其自行创建/关闭客户端。
4. **认证失败或限流后的无效请求。** 账号失效或明确限流后，暂停本轮该平台后续评论请求；连续三次访问被拒绝也会暂停。保留所有主帖和已得评论，剩余条目标记真实原因并可补抓；另一平台继续处理。重新补抓使用新的会话状态，不沿用上轮暂停标记。
5. **保持恢复语义。** 主帖 ID、平台、关键词、评论去重、逐次保存检查点不变。复用对象仅属于当前采集任务，不共享账号、代理或事件循环；不把凭证写入任务记录。

没有通过减少目标主帖数、评论采集上限或扩大请求并发来实现这次优化。

## 实测

`tests/manual/benchmark_comment_sessions.py` 使用真实本地 Chromium，交替运行三轮相同的 60 帖模拟内容。不访问平台，不使用真实 Cookie，不包含真实网络延迟或评论滚动。

| 项目 | 逐帖创建（旧路径） | 上下文与页面复用 |
| --- | ---: | ---: |
| 每轮处理主帖数 | 60 | 60 |
| 创建上下文数 | 60 | 3 |
| 创建标签页数 | 60 | 3 |
| 三轮耗时中位数 | 3.403 秒 | 0.723 秒 |
| 每轮结束残留上下文 | 0 | 0 |

本地模拟环节耗时下降 78.8%，资源创建次数下降 95%。这不是实际平台整轮任务的加速比例；真实任务的网络、页面滚动、评论总量和平台限制可能占主要耗时。仅复用上下文的初次实验改善约 1%，因此最终增加了页面复用。

原始数据：`work/comment-efficiency-2026-10-22/browser-benchmark.json`。

## 验证与边界

- 完整回归：316 passed、8 deselected（52.65 秒）。
- 新增 21 项用例覆盖：200 个 X 主帖仅创建 10 个上下文、跨任务账号/代理隔离、关闭后重建、取消保留评论与更新 Cookie 续抓、Reddit 50 个主帖复用 1 个 HTTP 客户端、Cookie 轮换、普通缺口不指数等待、真实故障保持退避、暂停后继续另一平台及恢复、页面清空、失败丢弃、拦截器仅注册一次。
- 本轮最终连续压力测试：5 轮 × 59 用例 = 295 次通过；每轮结束线程数 1、打开文件描述符 5，最后一轮测试进程峰值 RSS 540.4 MiB。资源关闭断言全部通过；峰值值本身不能证明长期内存绝无增长。原始结果见 `work/comment-efficiency-2026-10-22/pressure-soak.json`。覆盖原发布压力、图片、评论恢复及新增效率场景。
- 本轮未改动前端交互；此前工作台改造的截图与浏览器回归见 `work/workspace-redesign-2026-10-22.md`。
- 未进行真实账号长时间采集或 Win11/WebView2 实机验证，不能保证平台不报错，也不能承诺固定加速倍数。仍需安装包含修改的新版本才能对用户运行任务生效。

主要实现入口：`src/collection/comment_session.py`、`src/collection/engine.py`、`src/crawlers/twitter_url.py`、`src/crawlers/reddit_crawler.py`、`src/crawlers/comment_state.py`。
