# 评论分轮采集与增量保存（v1.9.3）

2026-10-26。用户要求保持主帖先完成，再优化评论；严格测试通过后推送并发布。

## 实现与边界

- `src/collection/comment_queue.py`：平台内每批两帖；全部关键词首轮优先；90/300/600 秒预算，最多三轮；有新增的缺口与临时故障有条件续排，没有新增的缺口不立即循环。超时保留 partial/failed，绝不充当 finished。
- 一个平台一个队列，两个平台仍依次执行；全局 `Traffic` 门闸包围整个有限批次。没有扩大同平台多个采集任务的总并发。网络/5xx 降为单路，认证/限流/连续 403 暂停后续未发出的任务。
- `src/crawlers/comment_policy.py`：ContextVar 区分队列尝试与旧独立调用，避免叠加两层重试；旧独立抓取接口保留兼容行为。
- `CommentSession.twitter_lease`：有活动页时不回收上下文；两个空闲页可复用。队列取消或失败后等待所有子任务清理，再释放门闸。
- `RowIndex`：主帖键与每帖评论 ID 的任务内索引。X 遍历报告 delta，不反复 JSON 编码整个 replies_data；已有 ID 允许内容更新。跨主帖的关联保留。
- `Store.save_comment_delta`：`comment_updates` / `comment_replies` 增量表。每块一笔 FULL 同步事务；读基线和增量时使用同一个 SQLite 读事务。正常结束/取消时合并兼容快照。强杀后未合并增量需新版恢复，旧版不能读取它。
- 评论阶段定时结果转换约 2 秒节流，数据库块仍立即提交，最终/取消强制同步。图片仍在评论后下载；没有实现可靠分页游标或新的回复归属判定。

## 模拟基准

`benchmark.json`：真实采集引擎+临时数据库，模拟平台和 .005 秒/块网络等待；300 主帖 × 100 评论，每帖 5 块，交替单路/双路共 4 轮。每轮重读数据库校验 30000 条评论、正确主帖关联及资源门闸归还。

- 单路 16.955、16.856 秒；双路 7.826、7.773 秒；中位数约减少 54%。这不是与旧版真实平台任务的完整对照，也不是实际平台速度保证。
- 同一 50 帖分组、5000 评论的 JSON 体积模型，整组序列化 27178000 字节，增量块 222450 字节；不包含其他元数据、最终快照或数据库页写入，不能称为实际磁盘写入减少比例。
