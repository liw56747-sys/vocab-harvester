# v1.8.0 发布压力测试与验证记录

日期：2026-10-15。环境：本地 macOS / Python 3.12 / Playwright Chromium。所有账号、平台返回和数据库均隔离，未对真实 X/Reddit 账号发起压力流量。

## 发现与修复

初始压力场景 5 项中 2 项失败：24 个同时提交创建了 24 个后台线程；模拟慢 Excel 生成阻塞 API 事件循环。修复后通过。

- 手动采集在创建记录/线程前检查 8 个在途任务上限，超限 429；定时任务在创建抓取线程前由 4 个并发槽排队。
- 大文件生成移到线程，采集下载同时限制为 2 份；历史列表查询不占 API 事件循环。
- 恢复占用与检查点重置顺序调整，40 个重复恢复请求只启动 1 个，其余 409，不修改在途检查点。
- 完成结果缓存保留 3 份且合计最多 64 MB。超限只释放内存中的文件内容，可从持久化记录重建。移除旧审核遗留的全文缓存。
- Reddit 的扁平评论与 X 的嵌套评论按各自真实结构测试，补齐导出 comment_id 及定时转换后的评论 ID。

## 持续压力循环

最终修复提交在同一 Python 进程连续执行 10 轮压力套件，110 个场景全部通过，总耗时 158.6 秒；进程累计峰值 RSS 469.9 MB，第 2–8 轮峰值约 464 MB，第 9–10 轮升至约 470 MB。测试每轮结束执行垃圾回收；该结果不是多日无泄漏证明。

## Windows 首轮远端发现

Windows 首轮流水线在 81 项通过后，双平台评论测试超过脚本固定 10 秒等待期限；日志显示已有 200 条主帖且仍持续保存，状态为 running，并非主程序崩溃。macOS 同一提交通过打包自检，发布阶段因 Windows 失败自动跳过，未公开 v1.8.0。

后续调整：SQLite 使用 WAL + FULL 同步；相同数据和状态不再重复更新数据库。测试区分进展与停滞，连续 10 秒无新进展或总计超过 60 秒仍失败，不删改行数、评论、去重和导出断言。增加重复 100 次相同检查点不产生新写入的回归，最终本地全量 245 项通过。两平台将对修复提交重新完整执行。

## Windows 第二轮界面脚本兼容性

第二轮 Windows 全量测试通过；界面脚本按系统 cp1252 读取 UTF-8 HTML，抛出 UnicodeDecodeError。四个脚本统一显式 UTF-8，并通过 `check_release_ui.py` 顺序执行，子脚本任一失败立即退出，防止 PowerShell 多命令只反映最后一个退出码。此问题发生在测试读取资源环节，不是客户端白屏。

## 发布门槛

Windows 与 macOS 发布流水线执行完整测试（含上述压力场景）以及四个真实浏览器脚本。打包后运行 `--self-test REPORT.json`，以独立临时数据目录验证启动、数据库、静态页面、审核接口、检查点、CSV/XLSX、tzdata、平台模块导入与随包 Chromium，并核对版本号。任一步失败则不发布。
